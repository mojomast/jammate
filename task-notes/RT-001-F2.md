# RT-001 F2 — bounded drum MIDI storage

## Goal and base

Remove callback-reachable MIDI growth caused by the engine's own note generation.
Base for resumption: `eac59ba`. Applied by the orchestrator on `main` after a
real JUCE Linux test build became possible.

## Implementation and bound

`src/DrumMidiCapacity.h` calculates a prepare-time reservation. The engine clamps
sample rate to at least 8000 Hz, tempo to at most 260 BPM and swing to at most 60%.
The shortest step is `60 / 260 / 4 * 8000 * (1 - 60 * .009)` = 212.3077 samples.
Even allowing its 0.5-sample due tolerance, intervals exceed 211 samples.

For a maximum block size `N`, reserve
`9 * (9 * (floor(N / 211) + 2) + 64 + 9)` bytes:

- nine note-ons per step; two extra steps cover due-at-entry/endpoint rounding;
- 64 pending note-off slots, each consumed at most once in a block;
- nine cleanup note-offs when leaving timeline playback;
- nine bytes per short MIDI event: three data, four timestamp, two length.

Timeline and audition note-on scheduling are mutually exclusive. Human timing
changes event positions, not their count. BPM/swing changes during processing
cannot invalidate this worst-case bound. The processor rejects drum blocks
larger than its bus prepared at the same size. JUCE `clearQuick()` retains storage.

`prepareToPlay` now uses the bound instead of 256. No sizing operation was added
to the callback. The cosmetic drum meter CAS retry was also replaced with one
strong attempt: a UI drain may drop a meter update, but cannot force a retry.

## Executed evidence

Real pinned JUCE, GCC 14.2, Release, Linux x86_64. The `drums.midiCapacity` suite
uses a no-op `AudioPluginInstance` receiving the actual engine MIDI stream.

| Case | Result |
|---|---|
| original 256-byte reservation, dense 8000 Hz / 8192 block | **2115 bytes** observed; allocation probe >0 |
| bounded reservation, 4 rates × 4 block sizes | peak **2115 bytes**; within bound; stable storage; **0 observed allocations and 0 frees** |
| all five real JUCE drum suites | **5/5 passed** |

Rates: 8000, 44100, 48000, 96000 Hz. Blocks: 128, 512, 2048, 8192. Exercises dense
nine-voice patterns, mixed meters, alternating tempo/swing extremes,
humanization, timeline/audition transition, resume and stop. Largest reservation:
3897 bytes; reference 128-sample reservation: 819 bytes.

The Linux test wraps C `malloc`, `realloc`, `free` from statically linked objects
and routes ordinary C++ `new`/`delete` through those probes. Thread-local counters
are armed only around `DrumEngine::process`, after preparation; assertions and
logging run afterwards. Windows uses byte-bound/storage assertions but has not
run here and lacks the ELF heap wrappers. The original-buffer test deliberately
retains 256 bytes and proves the probe detects the real growth mechanism.

## Limitations / integration

This closes the fork-generated MIDI capacity hazard in the exercised engine
path. It does not establish allocation freedom for the entire processor, NAM,
host transport or arbitrary hosted plugins. A guest can alter its MIDI buffer.
G1 remains partial; scene timer delivery, Windows/ASIO and device measurements
still require execution. Changes to scheduling clamps or pending slots must
revise the helper and rerun this suite.
