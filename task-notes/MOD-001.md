## Contract implemented

Suite name: `AnalysisAudioRing`, registered with the `JAM_TEST` macro, so it
becomes the ctest test `jam.AnalysisAudioRing`. 19 test cases, 95 236 checks.

| Contract item | Test case |
|---|---|
| 1. empty ring | `emptyRingRefusesToPop` — pop fails on a fresh ring, destination untouched, occupancy and overrun stay 0, repeated failed pops stay harmless |
| 2. zero capacity | `zeroCapacityIsALegalPermanentSink` — `valid()` false, `capacity()` 0, 64 pushes all refused immediately, nothing stored, pop fails, ring stays inert and queryable |
| 2b. zero capacity counter | `zeroCapacityPushIsNotCountedAsOverrun` — pins the *observed* behaviour; see Known limitations |
| 3. single push/pop | `singlePushPopPreservesPayloadAndMetadata` — `sampleTime`, `sourceSampleRate`, `numSamples` and all 16 sample values, plus a second pop must fail |
| 4. FIFO order | `framesComeBackInProducerOrder` — 16 frames of distinct size/metadata, popped in order with per-sample comparison |
| 5. wraparound | `wraparoundPreservesTheFrameSequence` — 200 rounds against 4 slots (~50 index wraps), no loss/duplication/reordering, occupancy never exceeds capacity, no overruns |
| 6. full / overflow | `overflowOnAFullRingLeavesQueuedDataIntact` — 4th push refused, overrun +1, write index unchanged, and all 3 queued frames still pop correctly byte-for-byte (the rejected block targeted the oldest frame's slot) |
| 7. monotonic overrun | `overrunCountTracksExactlyTheFailedPushes` — 5 consecutive refusals → exactly 5; successful push does not move it; not reset by `reset()` |
| 8. no partial write | `rejectedBlockLeavesNoResidueInItsTargetSlot` — the rejected block would have targeted slot 0; slot 0 still pops as the original frame, then is reused cleanly by a shorter frame |
| 9. metadata under wraparound | `metadataStaysWithItsOwnFrameAcrossWraparound` — 5 frames with distinct sample clocks and capture rates pushed across two wraps, each pops with its own metadata (a leaked rate would be a wrong tempo) |
| 10. variable block sizes | `variableBlockSizesRoundTrip` — 1, 2, 127, 128, 512, 1024, 2048, each with per-sample verification |
| 11. oversized clamped | `oversizedInputIsClampedToTheMaximumBlock` — 4096-sample input clamps to 2048 and *succeeds*; head preserved verbatim, tail never copied; a clampable block fits any free slot; a full ring still drops it and counts it |
| 12. null / zero-length | `nullPointerAndZeroLengthPushesAreRejected` — three invalid push forms refused, no overrun recorded (ring was neither full nor disabled), queued frame intact, ring still usable |
| 13. reset() | `resetMakesTheRingEmptyAgain` — occupancy 0, pop fails, capacity and `valid()` preserved, queued data abandoned, overrun counter deliberately preserved |
| 14. pushedBlocks() | `pushedBlocksReportsCurrentOccupancy` — tracks every push and pop, bounded by capacity, consumer activity never counted |
| 15. stress/determinism | `stressSequenceIsExactlyReproducible` — 10 000 operations from a fixed-seed LCG, run twice, all seven result fields identical; also asserts the run really overflowed, really clamped, and reached full occupancy; LCG output pinned so the generator cannot drift |

Beyond the 15 items, three tests cover guarantees stated in the ring's own
header comment and in SPEC 7.1:

- `storageIsPreallocatedAndPushPopNeverAllocate` — replaces global
  `operator new`/`delete` to count heap traffic. Construction is exactly 1
  allocation of at least `capacity * kMaxAnalysisBlock * sizeof(float)`; 2000
  rounds of 6 pushes against 4 slots plus 5 pops (4000 overruns) allocate
  nothing; destruction allocates nothing. This is the only way to actually
  observe SPEC 7.1's "no heap allocation in the callback".
- `popCopiesOnlyTheValidSamples` — destination pre-poisoned, only `numSamples`
  entries written, tail untouched.
- `analysisFrameHasAFixedBoundedPayload` — `kMaxAnalysisBlock == 2048`, array
  size, trivially copyable and standard layout (the frame crosses the audio-thread
  boundary).

## Known limitations

**1. Documentation discrepancy — capacity-0 pushes are not counted as overruns.**
`AnalysisAudioRing.h:52-53` documents push() as "Returns false (and increments
the overrun counter) when the ring is full or **disabled**", and
`AnalysisAudioRing.h:10-11` calls a capacity-0 ring a "permanent-overrun sink".
The implementation returns at `AnalysisAudioRing.h:57` — before the counter is
touched — so a capacity-0 ring reports `overrunCount() == 0` forever and never
records a drop. The *safe* direction the brief cares about (never blocks, never
stores, never corrupts, never crashes) is fully proven; only the counter
semantics differ from the comment.

This is **not** fixed, and **not** worked around by weakening: the observed
behaviour is pinned by a dedicated, prominently-commented characterisation test
(`zeroCapacityPushIsNotCountedAsOverrun`) so the discrepancy cannot drift
unnoticed. The ring was not modified. If the orchestrator wants the comment
made true, the one-line fix is to move the `slots_ == nullptr` case to increment
the counter; that is a change to a frozen seam and therefore out of scope for
this worker.

Impact on the caller: `analysisOverrunCount` (SPEC 8.1) will read 0 for a
device that reports no analysis buffer at all, which is a diagnostics blind
spot rather than an audio-safety problem.

**2. Documentation discrepancy — `reset()` does not "stop accepting data".**
`AnalysisAudioRing.h:122-123` says reset() "Stops accepting data. Used at
device shutdown." The implementation (`AnalysisAudioRing.h:124-128`) only zeroes
`writePos_` and `readPos_`; storage stays live and pushes still succeed
afterwards. `reset()` is a positions reset, not a disable. The test asserts the
implemented behaviour and flags the mismatch in a comment.

**3. Untested by design — actual thread safety.** The SPSC guarantee (exactly
one producer, one consumer) is enforced only by convention; this suite is
single-threaded per the "no threads" determinism rule. ThreadSanitizer coverage
is a separate job; the header's release/acquire ordering looks correct on
inspection (`push` publishes the payload with a release store of `writePos_`,
`pop` acquires it), but that is not proven here.

**4. Untestable as specified — `pushedBlocks()` across threads.** It reads both
positions and subtracts, so an observer on a third thread can transiently see a
value that never existed. It is only exact from the producer or consumer side.
Every assertion about it in this suite is made single-threaded.

**5. Not covered — 64-bit counter rollover.** The header claims the code
"degrades safely" because ordering comparisons use signed-safe modular
differences. Reaching `UINT64_MAX` needs ~1.5 million years at 48 kHz, so this
is not practically testable and is not attempted.

## Integration notes

The orchestrator must expect the ctest name **`jam.AnalysisAudioRing`** (1 test,
generated by `jam-core/CMakeLists.txt:113-115` from the `JAM_TEST` registrations
found by GLOB). Configure prints:

```

```

No CMake edits were needed or made — `jam-core/CMakeLists.txt` discovers
`tests/jam/*.cpp` by GLOB with `CONFIGURE_DEPENDS`, so adding
`AnalysisAudioRingTests.cpp` was sufficient.

The next wave will see one suite in jam-core; if a parallel worker also adds a
`tests/jam/*.cpp`, that worker's suite will appear alongside this one and
ctest will register both. No conflict.

Two global `operator new`/`delete` replacements live in this test file to count
heap traffic. They are file-local replacements (linkage is per-program, not
per-file) — if another jam test file ever defines its own, there will be a
duplicate-symbol link error. That is the one coupling worth knowing about; the
counters are guarded by `AllocationScope`, so they cost nothing until a test
asks for them.
