# RT-004 — bounded NAM architecture processor coverage

**Branch:** `wp/RT-004-nam-architectures` (base `bcf540a`).
**Doc:** `docs/research/NAM-ARCHITECTURE-PROBE.md`.
**Artifacts:** `docs/research/nam-architecture-probe/`.

## Outcome

- 5 predeclared model types x 2 variants (repaired current processor, original control), one clean process each, 26 cases each.
- **7 measured-clean, 3 measured-findings, 0 unmeasured, 0 failed.** Coverage complete.
- **Findings (not suppressed):**
  - `a2_wavenet_max` (`wavenet_a2_max.nam`) is positive on the **repaired** archive: 491520 warm heap allocs (2.0/host sample at 48 kHz, 1.0 at 96 kHz), matched frees, zero locks. Identical in the original control, so the RT-003 LSTM repair does not cover this architecture. Call sites: `ActivationPReLU::apply` and `BlendingActivation::apply` (upstream NAM activation code). Not repaired here.
  - `lstm.nam` on the original control reproduces RT-002 (2.0/sample). On the repaired archive it is zero (RT-003 holds).
- Non-finite / malformed / missing-case / identity / sourcepin errors are fail-closed. The fixture suite exercises each case.

## Scope and what was not done

- No processor, editor, DrumEngine, NAM vendored, shared CMake, ledger, HANDOFF or DEVPLAN change. No probe source change; `tools/processor-probe/**` read-only.
- No architecture repair (the A2/WaveNet activation allocations are a finding only).
- No ASIO/device/Windows/whole-program/realtime-deadline/hosted-plugin claim.
- Activation not isolated (every model activated during the dry run; NAM cold rows are post-prepare).
- Cold-path cannot see nothrow/aligned `new` (not CSV columns). Warm totals include them.
- `SlimmableContainer` measured on its default (last) submodel only; processor never calls `SetSlimmableSize`.
- Per-sample output not checked (probe gives mean warm `out_rms` only). The ~9 RMS on two models is recorded, not judged.
- Four example models outside the 5-type cap were not measured.
