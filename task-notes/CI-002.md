# CI-002

## Goal

CI-001 shipped the core+BTRack lane as an **expected-failure tripwire**: BTrack
had no adapter, so `-DJAM_ENABLE_BTRACK=ON` was asserted to *fail* with
"the adapter has not been written yet", and the job was built to go red the day
TRACK-001 landed. That day has arrived — **both** optional trackers are real
(TRACK-001 BTrack, TRACK-002 aubio) and `jam-core/CMakeLists.txt` wires both.
CI-002 replaces the obsolete tripwire with a genuine configure/build/ctest job
for every tracker configuration, keeps a machine-checked OFF boundary, retains
failure evidence, and reviews the checkout's Gitea-vs-GitHub assumptions and the
Windows lane's nested-submodule recipe.

## Contract implemented

**One job, four configurations.** `jam-core-trackers-linux.yml` step 3 configures,
builds and runs ctest for:

| Config | `JAM_ENABLE_BTRACK` | `JAM_ENABLE_AUBIO` | Suites at base `eac59ba` |
|---|---|---|---|
| `depfree` | OFF | OFF | 6 core |
| `btrack` | ON | OFF | 6 core + `jam.BTrackBackend` |
| `aubio` | OFF | ON | 6 core + `jam.AubioBackend` |
| `both` | ON | ON | 6 core + both |

All four are measured even if one fails; the job is red if any fails. Per-config
`*-configure.log`, `*-build.log`, `*-ctest.log` are printed on failure with a
2 MiB cap and the tail kept.

**Why a `for` loop, not `strategy.matrix`.** A matrix would give per-config
check names, but Gitea's support for `strategy.matrix` on this server is
unverified and an unsupported key kills a job before the first step runs — the
same failure mode as an unresolvable `uses:`, which CI-001 already refused to
rely on. The loop needs nothing the runner can lack. Recorded in CI-SETUP §2.3.

**The OFF boundary is a machine check, in every configuration.**
`libjam-core.a` and `jamTests` must contain zero
`BTrack`/`btrack::`/`kiss_fft`/`aubio` symbols (ON as well as OFF). In the
dependency-free config the build graph must not reference
`third_party/BTrack`/`third_party/aubio` at all, and a tracker configured OFF
must not register its suite. Enabled configs prove the other direction: the
suite is registered and real symbols are linked into the tracker test binary
(BTrack 5, aubio 136 at base).

**`JAM_CORE_BUILD_TESTS=ON` is passed explicitly.** After this task's base,
`jam-core` grew and honours that option. The job names it so its meaning does
not depend on a default. It deliberately does **not** assert the OFF side of
that option: the gating did not exist at `eac59ba`, so such an assertion would
make the job red on the commit it is committed to. A follow-up after rebase.

**No submodules in either Linux lane**, and the tracker lane asserts both
trackers are vendored and that JUCE was not materialised.

### 4. A measured false positive in the obvious boundary check

`nm -C build-aubio/libjam-core.a build-aubio/jamTests | grep -c aubio` returns
**2** — but both matches are `nm`'s own `path:` header lines, not symbols:

```console
$ nm -C build-aubio/libjam-core.a build-aubio/jamTests | grep 'aubio'
build-aubio/libjam-core.a:
build-aubio/jamTests:
```

The job strips header lines (`grep -Ev '^[^:]+:$'`) before matching; the true
count is 0. Without this the boundary would appear broken in exactly the configs
that are correct. Applied to the core lane too.

## Gitea vs GitHub checkout review

All three workflows build `CI_REPO_URL` from `${{ github.server_url }}` /
`${{ github.repository }}` and check out `${{ github.sha }}`. That is the
GitHub idiom that Gitea's `act_runner` exposes. The two Gitea-specific hazards
and their handling are in CI-SETUP §3.1: (a) a PR merge SHA that is not on a
fetched ref tip falls back to `refs/heads/*` + `refs/pull/*/head` and hard-fails
rather than checking out the wrong tree; (b) glob refspecs that match nothing
are tolerated by git. Server values remain assumptions A5/A6; nothing here was
observed on a live runner.

## Windows plugin lane review

`plugin-windows.yml`'s submodule recipe was re-verified from the pinned SHAs and
strengthened. `git submodule update --init --recursive third_party/NeuralAmpModelerCore`
is correct and necessary because the nesting is **two levels deep**:

| Path | Pinned SHA |
|---|---|
| `third_party/JUCE` | `91ad83ae…` (no `.gitmodules`) |
| `third_party/NeuralAmpModelerCore` | `1f42f885…` |
| `…/Dependencies/eigen` | `bc3b3987…` |
| `…/Dependencies/AudioDSPTools` | `0827c6c2…` (MIT; has its own `.gitmodules`) |
| `…/AudioDSPTools/Dependencies/eigen` | `6d829e76…` (only `--recursive` fetches this) |

The workflow now asserts all three nested gitlinks (NAM's eigen, AudioDSPTools,
AudioDSPTools' eigen), not just NAM's direct eigen, in addition to
`references/airwindows` being absent. A non-recursive init leaves AudioDSPTools
empty and the plugin cannot compile (`LanczosResampler.h`).

**The `git submodule update` commands were not executed here** (large, network
bound); the topology is measured from the pinned `.gitmodules`, the recipe is
not. Still not proven on Windows.

## Not proven / Known limitations

1. **No remote runner has run any workflow.** A green local run is evidence
   about the commands, not the server. Do not claim "CI is green" until a run
   exists in the Gitea Actions tab.
2. **`plugin-windows.yml` has never run anywhere.** `GuitarCompanion` has never
   been compiled on Windows. The strengthened submodule assertions are still a
   prediction; the `git submodule update` commands are unexecuted.
3. **Twelve server-side assumptions** remain unverified (CI-SETUP §3). A13 is
   not needed: no matrix is used.
4. **The ref-tip fallback is reasoned, not measured.**
5. **`JAM_CORE_BUILD_TESTS=OFF` is not asserted** — the gating post-dates this
   branch's base. Follow-up after rebase.
6. **No `actions/cache` and no `actions/upload-artifact`.** Both need an action
   whose availability is unverified; failure logs are printed with a 2 MiB cap
   instead. CI-SETUP §6 has the exact steps to add both.
7. **Linux toolchain install is unverified end-to-end** (no root here); package
   names were confirmed in the Debian archive by CI-001.
8. **The fixed required-suite subset** is a deliberate tripwire: deleting a
   listed suite turns the job red. Suites added after the base
   (`BackendRunner`, `RhythmDerived*`) still run but are not hard-required,
   except `BackendRunner`, which is required when its source exists.
