# CI-002

## Goal

CI-001 shipped the core+BTRack lane as an **expected-failure tripwire**: BTrack
had no adapter, so `-DJAM_ENABLE_BTRACK=ON` was asserted to *fail*, and the job
was built to go red the day TRACK-001 landed. That day has arrived — **both**
optional trackers are real (TRACK-001 BTrack, TRACK-002 aubio) and
`jam-core/CMakeLists.txt` wires both. CI-002 replaces the obsolete tripwire with
a genuine configure/build/ctest job for every tracker configuration, keeps a
machine-checked OFF boundary, **proves the ON side actually links**, retains
failure evidence, and reviews the checkout's Gitea-vs-GitHub assumptions and the
Windows lane's nested-submodule recipe.

A first commit (`4dfbc96`) was reviewed and found to have six gaps. This note
describes the final state **after** closing them (see "Review round 2").

## Contract implemented

**One job, four configurations.** `jam-core-trackers-linux.yml` step 3 configures,
builds and runs ctest for:

| Config | `JAM_ENABLE_BTRACK` | `JAM_ENABLE_AUBIO` | Suites at base `eac59ba` |
|---|---|---|---|
| `depfree` | OFF | OFF | 6 core |
| `btrack` | ON | OFF | 6 core + `jam.BTrackBackend` |
| `aubio` | OFF | ON | 6 core + `jam.AubioBackend` |
| `both` | ON | ON | 6 core + both |

All four are measured even if one fails; the job is red if any fails. Per-config
`*-configure.log`, `*-build.log`, `*-ctest.log` and `*.nm` are printed on failure
with a 2 MiB cap and the tail kept.

**Why a `for` loop, not `strategy.matrix`.** A matrix would give per-config
check names, but Gitea's support for `strategy.matrix` on this server is
unverified and an unsupported key kills a job before the first step runs — the
same failure mode as an unresolvable `uses:`, which CI-001 already refused to
rely on. The loop needs nothing the runner can lack. Recorded in CI-SETUP §2.3.

**The OFF boundary is a machine check, in every configuration.**
`libjam-core.a` and `jamTests` must contain zero BTrack/aubio/`kiss_fft` symbols
(ON as well as OFF), matched case-insensitively after `nm`'s header lines are
stripped. In the dependency-free config the build graph must not reference
`third_party/BTrack`/`third_party/aubio` at all, and a tracker configured OFF
must not register its suite.

**The ON boundary is now measured, not claimed.** An enabled tracker must be
really linked: the test binary must carry third-party symbols and the adapter
archive must carry our adapter symbols:

| Config | Assertion |
|---|---|
| `btrack` | `jamBTrackTests` has `BTrack::` and `kiss_fft` symbols; `btrack/libjam-btrack.a` has `jam::BTrackBackend`; `libbtrack.a`/`libkiss_fft.a` exist |
| `aubio` | `jamAubioTests` has `aubio_` symbols; `aubio/libjam-aubio.a` has `jam::AubioBackend`; `libaubio.a` exists |

Measured at base: `BTrack::`=33, `kiss_fft`=5, `aubio_`=136.

**`nm` is run to a file; exit status AND a non-empty symbol output are
required.** Measured: `nm` exits 0 with empty output on an empty archive, and
exits 0 with "no symbols" on a stripped `bin/true`; only a corrupt/missing file
exits non-zero. The old `nm … 2>/dev/null | grep … || true` pipeline could
therefore false-green a corrupt or stub object. Both workflows now capture nm to
`*.nm`, check the status and a symbol line, then grep.

**Python 3 is required.** Current `main`'s `jam-core/CMakeLists.txt` registers
`jam.RhythmDerivedGenerator` only when `find_package(Python3)` succeeds, else it
silently omits it. Both Linux workflows install `python3` and require
`jam.RhythmDerived` (when `tests/jam/RhythmDerivedTests.cpp` exists) and
`jam.RhythmDerivedGenerator` (when the generator script and the CMake
registration exist). Base-safe: neither exists at `eac59ba`.

**Checkout fallback now fetches PR merge refs too.** The ref-tip fallback
fetches `refs/heads/*`, `refs/pull/*/head` **and** `refs/pull/*/merge`. Glob
refspecs that match nothing are tolerated (measured), so requesting merge refs
is safe on a server that does not expose them; the exact-SHA hard-fail remains
the guarantee that a wrong tree can never be tested.

**No submodules in either Linux lane**, and the tracker lane asserts both
trackers are vendored and that JUCE was not materialised.

## Review round 2 — the six gaps and how each was closed

1. **ON side only checked core ZERO + suite registration.** Now the enabled
   tracker binaries and archives are symbol-asserted (§Contract). No-op
   injection: a real binary with 4620 symbols but no tracker code (`jamTests`)
   yields `BTrack::`=0, `kiss_fft`=0 and the guard fires.
2. **`nm` errors suppressed by `2>/dev/null` and `|| true`.** Now nm runs to a
   file, and both status and non-empty output are required, in both workflows.
   Injection: empty archive (nm exit 0, empty) → fires; missing file (exit 1) →
   fires; corrupt archive (exit 1) → fires; `/bin/true` stub (exit 0, "no
   symbols") → fires.
3. **Windows `references/` check used directory presence.** Measured a fresh
   clone: git creates an **empty** directory for every gitlink (`third_party/
   JUCE`, `.../NeuralAmpModelerCore` are empty with no `.git`), while
   `references/*` have no gitlink and do not appear. The check now tests
   materialisation (`.git` file or non-empty contents), so a placeholder cannot
   false-positive.
4. **"Never compiled anywhere" contradicted the Linux build.** Corrected in
   `plugin-windows.yml` and CI-SETUP: the plugin **has** been built on Linux
   (Standalone + VST3, no root, extracted Debian dev headers —
   `docs/research/LOCAL-LINUX-BUILD.md`, main commit `677ce9f`). The unmeasured
   lane is **Windows/MSVC/VST3/ASIO**, and no Windows VST3 measurement exists.
   CI-SETUP no longer asserts Gitea hosting as fact — the ledger's "actual
   hosting and runners remain unverified" is quoted.
5. **`RhythmDerivedGenerator` could silently disappear without Python.**
   `python3` is now installed in both Linux toolchains, and the derived suites
   are required when their source/registration exists. Injection: configuring
   `main` with `-DCMAKE_DISABLE_FIND_PACKAGE_Python3=ON` drops the suite from
   `ctest -N`, and the requirement fires.
6. **Checkout fallback did not fetch merge refs.** `refs/pull/*/merge` added to
   all three fallbacks; glob tolerance measured (wildcard matching nothing
   exits 0; literal missing ref exits 128). The exact-SHA hard-fail is retained
   and the remaining limitation stated precisely (whether a server exposes merge
   refs is still unmeasured).

## Not proven / Known limitations

1. **No remote runner has run any workflow.** A green local run is evidence
   about the commands, not the server. Do not claim "CI is green" until a run
   exists in the Actions tab. The forge/hosting is itself unverified (ledger).
2. **`plugin-windows.yml` has never run and the plugin has never been built on
   Windows.** Linux Standalone+VST3 **have** built (`677ce9f`,
   `docs/research/LOCAL-LINUX-BUILD.md`); that is a Linux result. **No Windows
   VST3 measurement exists.** The `git submodule update` commands are unexecuted
   on Windows.
3. **The ref-tip fallback's reachability of a specific PR merge SHA is
   unmeasured** — it depends on what the server exposes. The exact-SHA hard-fail
   means a failure is a red job, never a wrong tree.
4. **`JAM_CORE_BUILD_TESTS=OFF` is not asserted** — the gating post-dates this
   branch's base. Follow-up after rebase.
5. **No `actions/cache` / `actions/upload-artifact`.** Failure logs are printed
   with a 2 MiB cap. CI-SETUP §6 has the exact steps to add both.
6. **Linux toolchain install is unverified end-to-end** (no root here); package
   names were confirmed in the Debian archive by CI-001.
7. **Fixed required-suite subset.** Deleting a listed suite turns the job red.
   Newer suites still run; the added ones are hard-required when their
   source/registration exists.
