## Evidence

The decisive evidence:

- `src/PluginProcessor.cpp:1227` — `triggerAsyncUpdate();` textually inside
  `processBlock`, in `case SceneEnv::fadeOut:`, guarded by
  `if (g1 <= 0.0f)` (lines `:1218-1229`).
- `src/PluginProcessor.cpp:2640-2648` — `processDrums` (called from `processBlock:1270`)
  calls `armSceneEnvelope(sec)` when `scenesOn` and a scene-armed section is entered;
  `armSceneEnvelope` (`:2440`) sets `sceneEnvState = fadeOut`.
- JUCE 8.0.4 source: `triggerAsyncUpdate` → `MessageBase::post` →
  `MessageManager::postMessageToSystemQueue` → Windows `InternalMessageQueue::postMessage`
  takes a `ScopedLock` and calls `PostMessage`. Upstream doc (verbatim, quoted in the
  audit): calling it from a real-time thread "involves posting a message to the system
  queue, which means it may block".
- `juce::MidiBuffer` stores events in `Array<uint8>`; `addEvent` may reallocate. The drum
  path adds events at `src/DrumEngine.cpp:233-234` and `:383`, against a reservation of
  only `ensureSize(256)` at `src/PluginProcessor.cpp:1019`.

## Known limitations

- **No runtime proof.** ADR-0003 forbids building the JUCE target here, so the zero
  allocation/message-post gate (§18.1) is not measured; it is argued from code and JUCE
  source. The instrumentation plan in `RT-REACHABILITY.md` §5 is the intended follow-up.
- **F2 is conditional and not observed.** Whether a hosted drum VST3 can exceed the
  256-byte `drumMidi` reservation in one block is argued from capacity, not measured;
  the finding is explicitly scoped as "probable, not proven zero".
- **Third-party internals are unauditable** (NAM, resampler, hosted VST3s). They are
  named as accepted risk, not cleared.
- `src/jam/AnalysisAudioRing::push` is allocation-free today but is **not yet called**;
  when INT-ANALYSIS-001 wires the tap it becomes a new callback-reachable site and must
  be re-audited. This is a named gap, not a guessed green.
- Line references are valid at the base commit only.
