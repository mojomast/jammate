# MOD-002

## Goal
Implement `jam::DrumTransportAdapter` — a policy-free, boundary-quantising
scheduler that implements the frozen `jam::IDrumTransport` seam — plus
deterministic unit tests driven entirely through a sample-clock `advance()` API.
The adapter lets the Jam Director control drums without `DrumEngine` ever
learning that beat tracking exists, and without the adapter ever selecting,
smoothing or inferring tempo.

## Contract implemented
All of `IDrumTransport`: `prepare`, `startTransport`, `stopTransport`,
`setClockTempo`, `requestResyncNextBeat`, `requestResyncNextBar`,
`queueBarChange`, `requestFillAtNextBar`, `requestStopAtNextBar`, `position`.
Plus concrete-only scheduling surface: `advance(uint64_t)`,
`applyClock(const ClockSnapshot&)`, and read-only diagnostics/counters/event log.

Tempo enters through exactly one private path: `applyClock` → `setClockTempo` →
`clampBpm`. `setClockTempo` carries no lock state, so it does not overwrite a
`Lost`/`tempoFrozen` state set by `applyClock`. The adapter never calls a
detector, never smooths, never predicts.

## Boundary policy
- `queueBarChange`: appended to a fixed-capacity FIFO. It does **not** apply
  immediately. It applies at the first bar boundary `advance()` reaches after
  queueing. While the transport is stopped it is held and applied on the
  bar-1 downbeat when `startTransport` runs.
- Multiple bar changes for the same boundary: the last-queued (highest
  generation) one wins (`last-write-wins`); a change whose generation is
  strictly older than the newest pending bar change is dropped at enqueue and
  counted (`staleDropCount`). The boundary writes the applied state **once**
  (`appliedBarChangeCount`), while every queued entry is retired exactly once
  (`consumedChangeCount`).
- `requestFillAtNextBar`: same FIFO (distinct kind), coalesced the same way,
  applied at the next bar boundary; writes only the fill field.
- `requestResyncNextBeat` / `requestResyncNextBar`: scheduled at the exact
  `targetSampleTime`; applied when `advance` reaches it. The grid is re-anchored
  at the target so the correction affects only samples at/after it, and the
  integer beat (resync beat) or integer bar (resync bar) is preserved, so the
  bar counter cannot jump or rewind. Mirrors `MusicalClock::applyResync`.
- `requestStopAtNextBar`: a dedicated flag (never droppable by a full buffer).
  At the next bar boundary the transport stops, pending musical changes are
  discarded and counted (`droppedAtStopCount`), and `samplePosition` is frozen
  exactly on the boundary.
- Tempo: `applyClock`/`setClockTempo` stage a new tempo that is re-anchored at
  the next `advance` block-start, so the rate changes without a phase
  discontinuity. Tempo is not bar-quantised (only the smoothed clock ever
  produces it, and SPEC 3.4 quantises *pattern* changes, not tempo corrections).

## Overflow policy
Fixed capacity `TransportConfig::maxPendingChanges` (≤ `kMaxPendingChanges = 16`).
When full, the **newest incoming** change is dropped, `overflowCount` is
incremented, and the call returns immediately; already-queued entries are left
byte-for-byte intact. This is the same "drop the incoming item, count it, return
immediately" policy as `jam::AnalysisAudioRing` (SPEC 8.1/8.3). Stop is stored in
its own flag precisely so a full musical buffer cannot silently drop it.

## Position model
`samplePosition_` is a `uint64_t` sample counter, moved only by `advance()`.
Position is a pure function of that counter through an exact anchor:
`beats = anchorBeat + (sample − anchorSample) * bpm / (60 * sampleRate)`.
`bar = floor(beats / beatsPerBar) + 1`, `beat = floor(beats) % beatsPerBar + 1`
(frozen `TransportPosition` contract; `0`/`0` and `playing == false` when
stopped). Tempo changes and resyncs move only the anchor, never the accumulated
position, so `beats` is recomputed from the integer sample count every query.
Anti-drift argument: a float never accumulates; the only rounding is one
multiply-add of an integer delta per query. Test
`thirtyThousandBlocksDoNotDrift` runs 30 000 × 512 samples at 100 BPM and
matches the closed form to `1e-6` beat; the same run at 120 BPM is exact
(640 beats, bar 161, beat 1).

## Judgement calls
Where SPEC was silent, these were chosen and are listed for the orchestrator:
1. **Lost defers changes.** `lockState == Lost` means the ensemble grid is
   untrustworthy (SPEC 10.1), so a queued bar change is **deferred**, not
   discarded, until the lock recovers; `Acquiring` and `Holdover` are honoured.
   Configurable via `TransportConfig::honourChangesWhileLost`.
2. **Lost alone does not freeze tempo.** Only `ClockSnapshot::tempoFrozen`
   freezes tempo (`tempoIgnoredCount`). Freezing on `Lost` as well would be a
   second, undocumented tempo policy.
3. **Stop supersedes pending changes.** At the stop boundary, pending musical
   changes are dropped and counted rather than applied-then-stopped.
4. **Tempo rails are wide (20-400).** Deliberately wider than the clock's own
   50-220 range so a legitimate already-smoothed belief is never second-guessed;
   only nonsense (3, 1000) is clamped.
5. **Live meter changes are ignored while playing.** Meter is set by
   `startTransport`; changing it from a `ClockSnapshot` mid-run would reinterpret
   the current bar grid. Recorded as a DRUM-001 integration requirement instead.
6. **`setClockTempo` does not touch lock state** (it carries none); `applyClock`
   does.
7. **One bar boundary is processed per `advance()`.** Block sizes are expected to
   be far smaller than a bar (512 ≪ 96000 samples at 120 BPM). Advancing more
   than a full bar in one call processes only the first boundary; nothing is lost,
   but multiple boundaries are not wrapped. See Known limitations.
8. Event log stores the first `kMaxTransportEvents = 64` events;
   `totalEventCount()` keeps counting beyond that.

## Known limitations
- One bar boundary per `advance()` (judgement call 7).
- Live meter changes from the clock are not applied (judgement call 5).
- The no-allocation-after-construction property is structural (member arrays only,
  no containers/`new`), but is not asserted by an allocation-counting test the way
  `AnalysisAudioRingTests` does.
- When a resync and a bar crossing fall in the same block, the reported boundary is
  clamped to the block end; the intended tests keep them separate.
- `appliedChange()`/counters/event log are the adapter's only output. It cannot
  touch `DrumEngine` in this task (hard prohibition + header hygiene forbids JUCE),
  so DRUM-001 must connect that output to the engine.

## Integration notes
What DRUM-001 must do for the real `DrumEngine` to be driven through this seam.
The adapter currently cannot include `DrumEngine.h` (it pulls in JUCE, breaking the
platform-neutral jam-core build) and is forbidden from editing `DrumEngine.*` here,
so this is an explicit interface requirement, not a bypass.

Adapter assumptions / requirements on `DrumEngine`:
1. **Sample-accurate step scheduling.** `DrumEngine::process` already schedules via
   `samplesToNext`/`stepLenSamples(stepIdx)` — present. Today it reads
   `DrumEngine::bpm` directly; DRUM-001 must make the adapter's tempo the only
   writer so the detector can never write it (INT-JAM-001).
2. **Boundary-safe tempo update.** `stepLenSamples()` reads the live `bpm` atomic,
   so a mid-bar tempo write stretches the remaining steps. The adapter applies
   tempo at a block-start re-anchor; `DrumEngine` has **no** phase-continuous tempo
   update mechanism. Integration requirement: add one (or accept the block-grain
   quantisation).
3. **Swap pattern at a bar boundary.** `library()[LibraryIndex]` (`drum::Groove`) →
   `parseSpec`/`setBarPattern` exists, but there is **no** queued-swap-at-next-bar
   API. Integration requirement: a way to install a groove for the next bar
   downbeat without disturbing the bar in flight.
4. **Queue a fill at a requested bar.** The library carries fills (`Groove::fill`),
   but `DrumEngine` exposes no queued-fill entry point. Integration requirement.
5. **Re-phase.** Resync needs to set `nextStep`/`samplesToNext`; both are private
   and there is no re-phase API. Integration requirement for
   `requestResyncNextBeat/Bar` to actually take effect in the engine.
6. **Transport counters.** The adapter owns authoritative `samplePosition`/bar/beat.
   `DrumEngine` exposes `uiBar`/`uiStep`; DRUM-001 should drive/align those from the
   adapter, not the other way round.
7. **Stop at bar.** `DrumEngine::playing` can be cleared at the boundary; no new
   engine capability needed.
8. **Intensity/humanize/swing.** `DrumEngine` already has `humanVel`, `humanTime`,
   `humanRR`, `swingPct` atomics; DRUM-001 writes them from
   `appliedChange()` on the control thread.
9. **Time source.** The host must call `DrumTransportAdapter::advance(numSamples)`
   once per processed block (control thread) with the same frame count the audio
   thread rendered; otherwise the sample clock and the audio engine diverge. This
   is a required integration contract.
10. **Output hand-off.** Because a parallel push interface inside `DrumEngine` would
    be forbidden, the adapter exposes `appliedChange()`, its counters and its
    bounded event log; DRUM-001 polls these on the control thread and publishes to
    the engine atomics. If the orchestrator prefers a push sink owned by the
    integration, that is a DRUM-001 decision, not a change to the frozen interface.
