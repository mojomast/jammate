## Contract implemented

**Runner labels** — `ubuntu-latest` / `windows-latest` only, per instruction. No
invented labels, no self-hosted labels.

**No submodule init in the core lane**, and each core job *asserts*
`third_party/JUCE/CMakeLists.txt` was not materialised, with a comment saying
why, so a later `--recursive` is caught by CI instead of being "fixed" in.

**Ninja, not the Makefiles generator — and why.** `jam-core/CMakeLists.txt`
lines 11–12 document the standalone recipe as `-G Ninja`, so Ninja is the
project's own convention. The "fewer moving parts" argument for Makefiles does
not survive contact with reality here: this lane needs `cmake` **regardless**,
so an `apt-get install` is unavoidable and `ninja-build` is one more package
on the same line. Choosing Makefiles would mean installing cmake and then
deliberately not using the documented generator.

**ctest is never allowed to pass silently.** `ctest` exits **0** on an empty
build directory (measured, below), so every job parses `ctest -N` for
`Total Tests: N` and hard-fails if it is absent or `< 1`, *before* running. The
core jobs additionally assert each of the five `jam.*` suite names is registered.
The runner's own non-zero-on-empty-filter is left as the second line of defence;
no job wraps `ctest` in `|| true`, and no step has `continue-on-error`.

**Log only on failure, only if small** — `if: failure()` step, 2 MiB cap per
file, tail kept. No artifact upload; see "Assumed but unverified".

**Every job can fail.** No `--warn-as-error`, no `|| exit 0`, no dropped
targets, no `continue-on-error` on any build or test step. Proven in
"Failure-path evidence".

**Action availability is the one assumption I refused rather than documented.**
The three workflows reference **zero** actions. `actions/checkout@v4` does not
resolve by default on Gitea (it does not reach `github.com` for marketplace
actions), and an unresolvable `uses:` kills a job during job preparation —
`continue-on-error` cannot save it, because the step never starts. There is no
version of "swap in `actions/checkout` later" that is cheaper than "just use
git", and `git` is the one tool every runner is guaranteed to have. The same
reasoning removed `actions/cache` and `actions/upload-artifact`;
`docs/research/CI-SETUP.md` §6 has the exact steps to add them back once the
server is confirmed. Pinning is moot: nothing is referenced by version.

**Two Gitea behaviours I could have got wrong and did not.**

1. `command -v sudo` is **not** a valid test for passwordless sudo — sudo can be
   installed and still demand a password. My first version used it and produced
   `sudo: a password is required` instead of a useful message. Caught by running
   it; fixed to `sudo -n true 2>/dev/null` and the guard now names the three
   packages it wanted.
2. A step name containing `: ` (`Configure jam-core (default: JAM_ENABLE_BTRACK=OFF)`)
   makes YAML read a **mapping** and the whole file fails to parse. Caught by the
   parser, fixed by quoting.

first run is the lane's first measurement, not a broken pipeline.

## YAML validation

**A real parser was used: PyYAML 6.0.3**, `yaml.safe_load`, plus a structural
checker. PyYAML was *not* installed initially
(`ModuleNotFoundError: No module named 'yaml'`) and was installed into the
existing venv with `pip install pyyaml`; no claim here rests on a structural
eyeball check.

The `uses:` count is a raw substring count, so the `2` in the core file are the
words ``Uses NO `uses:` actions`` in a comment; the per-step check confirms no

**One validator caveat, stated rather than hidden:** PyYAML implements YAML 1.1,
in which the bare key `on:` resolves to boolean `True`. GitHub Actions and
Gitea's act_runner (`gopkg.in/yaml.v3`, YAML 1.2 core schema) both read it as
the string `"on"`. The validator accepts either. Unquoted `on:` is what every
GitHub Actions workflow uses, so it was left alone.

## Known limitations

1. **`plugin-windows.yml` has never run.** §Not proven. Everything in it is a
   prediction except the submodule topology, which was read from the pinned
   SHAs.
2. **Twelve server-side assumptions** are unverified. §Assumed but unverified.
3. **No caching and no artifact upload.** Both need an action whose availability
   is unverified, and an unresolvable `uses:` cannot be caught with
   `continue-on-error`. DEVPLAN §9 step 6/7 are therefore satisfied in spirit
   (cold runs are the norm, so correctness cannot depend on a cache; logs are
   printed on failure with a 2 MiB cap) but not literally.
   `docs/research/CI-SETUP.md` §6 has the exact steps to add both.
4. **A private repository would not clone.** The workflows use no credentials,
   as required. Fixing that needs a server-side secret and is deliberately out
   of scope. Do not paste a token into a workflow file.
5. **The build-directory cache, if ever added, must key on the source hash**, not
   the branch, or a green run can restore a stale tree.
6. **The five hardcoded suite names** in the core jobs are a maintenance trap by

   coverage. Adding a suite does not break it.
7. **The plugin job builds `ALL_BUILD`** rather than naming

8. **Linux toolchain install is unverified end-to-end** (no root here). Package

9. `task-notes/ci-validate.py` and `task-notes/ci-run-steps.sh` are outside the
