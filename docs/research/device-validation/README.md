# Device validation protocol and evidence (DEVICE-002)

Scope: `tools/device-validation/` collects and validates the physical-interface
evidence the SPEC keeps separate from software tests. It produces no measurement
by itself. This directory holds the protocol, the tooling self-test output and
the outstanding physical-evidence list.

Base worktree: `wp/DEVICE-002`, base `984ad1d` (adaptive build wave contract).
Owned paths: `tools/device-validation/`, `docs/research/device-validation/`,
`task-notes/DEVICE-002.md`. No shared CMake/CI/ledger/source/history is touched.

## What is measured vs unmeasured

| Class | Backing required | Where it is allowed |
|---|---|---|
| Physical round-trip latency | a recorded loop-back WAV, re-analysed from bytes | `device-validation/latency/1.0` |
| Callback p50/p99, deadline misses, analysis overruns | a raw instrumentation receipt named explicitly | `device-validation/play-trial/1.0` `callback` |
| Play timing, dropouts, useful-lock window/time | a raw receipt | `play-trial` timing/lock/dropouts |
| Operator judgements (SPEC 20) | none; always `operator-report` | `play-trial` `judgements` |
| Device disconnect / channel change / silent / clipped input | a raw log/trace/WAV receipt | `device-validation/functional/1.0` |

A number marked *measured* without its receipt is a hard validator failure.
Callback measurements never establish physical monitoring latency: only a
`latency` record with `analysis.valid: true` does.

## Identity and anti-fabrication rules

- Every record stores product (`Guitar Companion`), source git SHA, build kind,
  backend, driver, device names, sample rate, block frames and monitoring mode.
- Every raw file and receipt is stored with its sha256 and byte size, and the
  validator re-hashes it from disk.
- The validator re-derives each latency from the WAV using the recorded
  parameters; an edited `physical_roundtrip_latency_ms`, `valid`, `reasons` or
  `target_met` is rejected.
- A record's interface identity must match the session manifest exactly.
- `synthetic: true` records are labelled and excluded from every physical gate.

## Release hardware matrix (SPEC 21.5)

| condition | kind | required evidence | numeric target |
|---|---|---|---|
| `asio_48k_64` | latency | Windows ASIO, identified driver, physical WAV | none |
| `asio_48k_128` | latency | Windows ASIO, identified driver, physical WAV | `<= 12 ms` (SPEC 18.3) |
| `asio_48k_256` | latency | Windows ASIO, identified driver, physical WAV | none |
| `wasapi_low_latency` | latency | Windows WASAPI, physical WAV | none |
| `device_disconnect_reconnect` | functional | receipt | pass |
| `input_channel_change` | functional | receipt | pass |
| `silent_input` | functional | receipt | pass |
| `clipped_input` | functional | receipt | pass |

The release gate is `--gate all`: the hardware matrix **and** all six SPEC 20
play conditions. An empty matrix never passes.

## Local availability (factual)

`environment.json` (from `probe_environment.py`, read-only) records this machine:
no `/dev/snd`, no `/proc/asound/cards`, no PipeWire socket, and no
`arecord`/`aplay`/`pw-record`/`sox`/`aplay`; only `ffmpeg` is present. No audio
interface, ASIO driver or Windows host is available here, so **no physical
latency, play-trial or ASIO evidence was or could be produced**. No packages were
installed.
